# Решение тестового задания

## Запуск

```sh
node server.mjs
```

Откройте http://127.0.0.1:3000. Порт меняется переменной `PORT`. Нужен Node.js 20 или новее, зависимостей и ключей нет.

## Тесты

```sh
npm test
```

Эквивалентно `node --test`. 26 тестов, внешних зависимостей нет: юнит-тесты логики, интеграционные тесты через настоящий HTTP и тесты страницы на её реальном скрипте из `index.html`.

## Что сделано

| Файл | Назначение |
| --- | --- |
| `app.mjs` | HTTP-слой: разбор тела, валидация входа, ответы 200/400/404 |
| `triage.mjs` | Логика: вызов модели с лимитом 300 мс и проверка её ответа |
| `server.mjs` | Тонкая обвязка: читает `index.html`, слушает порт |
| `index.html` | Страница: тема + черновик при успехе, сообщение при сбое |
| `test/triage.test.mjs` | Тесты API и логики, включая все сценарии сбоя |
| `test/ui-clear.test.mjs` | Тесты страницы: очистка предыдущего черновика при сбое |
| `mock-ai.mjs` | **Не изменён** — поведение выданного имитатора прежнее |

## Где проверяется результат AI

Две точки контроля, обе до показа менеджеру:

1. `extractRequestText` (`app.mjs`) — вход. Битого JSON, необъекта, отсутствующего `text`, нестрокового значения, пустой строки и строки из пробелов достаточно для `400 {"status":"invalid_input"}`.
2. `normalizeModelReply` (`triage.mjs`) — ответ модели. Он должен быть JSON-объектом, тема — из списка `delivery` / `pricing` / `other`, черновик — непустая строка после `trim()`. Любое несовпадение — не «почти готовый» черновик, а `manual_review`.

## Что происходит при сбое

`triage()` не бросает исключений: таймаут (модель думает дольше 300 мс), исключение модели, не-JSON, недопустимая тема, пустой черновик — всё сводится к `200 {"status":"manual_review","topic":null,"draft":null}`.

На странице это выглядит так: блок с темой и черновиком скрыт, предыдущий черновик очищен, менеджер видит сообщение «Модель не смогла разобрать заявку. Прочитайте текст и ответьте клиенту вручную — черновик не создан». Введённый текст заявки не теряется, поэтому можно повторить попытку. Отдельно обработаны недоступность сервиса и ответ 400.

Почему не 500: сбой модели — ожидаемая рабочая ситуация, а не ошибка сервера. Клиент всегда получает разбираемый контракт, менеджер — понятное действие.

## Как проверял

- `npm test` — 26 тестов. Сценарии `[timeout]`, `[error]`, `[bad-json]`, `[bad-topic]`, `[empty-draft]` дают `manual_review`; пустой, пробельный, нестроковый и отсутствующий `text` и битый JSON дают 400; обычный текст даёт `ready` с темой `delivery` / `pricing` / `other` и непустым черновиком. Таймаут проверяется по замеру времени (ответ приходит около 300 мс, а не через 1200 мс сна имитатора).
- Очистка предыдущего черновика проверяется автоматически, на реальном скрипте страницы: `test/ui-clear.test.mjs` берёт inline-скрипт из `index.html`, подменяет DOM минимальной заглушкой и `fetch`, и прогоняет сценарии «успех → сбой» для `manual_review`, сетевой ошибки, `invalid_input` и пустого ввода. Тест не пустой: если убрать вызов `clearResult()` из обработчика, падают три кейса.
- Ручные HTTP-проверки по всем сценариям (`timeout` — 301 мс, сбои — 200 `manual_review`, негодный ввод — 400).

## Польза

Менеджер не пишет ответ с нуля и отвечает единообразно, а спорные заявки сразу помечаются для ручного разбора. Мерить: среднее время от поступления заявки до первого ответа и доля ответов, отправленных без правок черновика (до/после внедрения).
